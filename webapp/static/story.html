A Game Boy, running as ClickHouse SQL

Same idea as the CHIP-8 project in this environment, scaled up: a Sharp LR35902 CPU and tile-based PPU implemented entirely as SQL functions, proven by booting a real (open-source) Game Boy boot ROM.

Why start with the boot ROM

The Game Boy CPU has roughly 500 opcodes (256 unprefixed + 256 CB-prefixed bit operations) versus CHIP-8's 35 - implementing all of it up front wasn't the right first step. Instead, this mirrors the CHIP-8 project's own first milestone: disassemble one small, well-understood program, implement exactly the opcodes it needs, and validate against real output. SameBoy's DMG boot ROM turned out to need only ~35 distinct opcodes - about the same size as CHIP-8's full instruction set.

Getting the ROMs legally

The actual Nintendo boot ROM is copyrighted and not freely distributable. Instead this uses SameBoy's open-source (MIT/Expat licensed) clean-room replacement boot ROM, assembled from source with rgbds (the standard homebrew toolchain) rather than downloading any binary. The test "cartridge" is one built from scratch with a trivial infinite-loop program - its header's mandatory Nintendo logo bytes (required by every Game Boy ROM to boot on real hardware, part of the file format itself) were filled in by rgbfix -v, a standard rgbds tool, not extracted from any commercial ROM dump.

Same architecture as CHIP-8, same pitfalls found faster

CPU state (16KB+ memory as a full 64KB flat array, all eight 8-bit registers, SP/PC, IME, and a running T-cycle counter) is one ClickHouse Tuple. gb_step(state) -> state decodes and executes one instruction; arrayFold runs it N times per batch inside a single query, exactly like CHIP-8's ch8_run_batch.

A bigger version of CHIP-8's chaining pitfall. CHIP-8 taught that ClickHouse UDFs are macro-expanded at each call site, not opaquely compiled, so chaining calls outside arrayFold explodes the query tree. Here the same mechanism bit a single instruction: helper functions like gb_write8 and gb_set_hl each re-reference their input state ~13 times internally (to carry every untouched register field forward). Chaining just two or three of these (gb_set_hl(gb_write8(gb_write8(s, ...), ...), ...) for something like CALL, which pushes two bytes then jumps) multiplies that 13x at each level - 2-3 levels of chaining pushed a single opcode's expansion past ClickHouse's 500,000-node query-tree limit, even inside arrayFold. The fix: generate every opcode handler as one flat gb_mk(...) call, computing all 15 fields directly from accessors on the one original state parameter, never from another function's state-tuple output. With ~35 opcodes each needing a 15-argument call, this was written by a small Python generator (gen_step.py) rather than by hand - see the Explore tab.

The PPU

Background-only for now (no window layer, no sprites - the boot ROM doesn't use either): for each of the 160×144 screen pixels, look up its tile from the 32×32 tile map at 0x9800, fetch that tile's row from tile data at 0x8000 (2 bits per pixel, stored as two bit-planes), and run the result through the BGP palette register. All pure, read-only scalar functions - the same "small composable helper called repeatedly inside one arrayMap" pattern CHIP-8's sprite-drawing code used.

Result

Running the assembled boot ROM against the from-scratch cartridge for ~25 frames (each frame = 70,224 T-cycles, most of it spent busy-looping in the boot ROM's own VBlank-wait poll - meaning a single frame is actually tens of thousands of individual SQL-executed CPU instructions) renders the real SameBoy splash sequence: the Nintendo logo scrolls into place and the trademark symbol appears, pixel-correct, entirely from executing real Game Boy machine code through ClickHouse.

What's not here yet

This is intentionally scoped to "boot ROM works," not "plays games": no sprite or window rendering, no sound output, no interrupt servicing (the boot ROM only polls flags, never actually enables interrupts), no cartridge bank switching (MBC1/3/5), and only ~35 of ~500 opcodes. Next step is broadening opcode coverage toward Blargg's cpu_instrs test ROM - the Game Boy equivalent of CHIP-8's corax+ opcode-correctness suite.
